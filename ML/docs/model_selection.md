## 一、候选模型：选哪 2~3 个来测，为什么

不是随便选,选之前先看这几个维度：这个模型在 Bedrock 里**是否好申请到权限**、**贵不贵**、**擅不擅长严格按格式输出 JSON**。基于这些,建议测试下面 3 个：

| 模型                                   | 提供方    | 为什么选它做候选                                                                                  |
| -------------------------------------- | --------- | ------------------------------------------------------------------------------------------------- |
| **Claude 3.5 Haiku**             | Anthropic | 便宜、速度快,Anthropic 家族对"严格按 JSON schema 输出"支持得好,适合当"性价比选手"                 |
| **Claude 3.5 Sonnet**            | Anthropic | 比 Haiku 贵和慢,但理解力更强,适合当"精度上限"参照,看贵的是不是真的更准                            |
| **Amazon Nova Lite（或 Micro）** | Amazon    | AWS 自家模型,Bedrock 里通常最容易申请到权限、价格也很低,适合当"平台原生选手"对比一下 Anthropic 系 |

**为什么是这 3 个而不是别的：**

- 都支持 Bedrock 的 **JSON 输出模式/工具调用**（可以约束格式,不是纯靠 prompt 硬要求）,公平对比"听话程度"才有意义
- 覆盖了"贵 vs 便宜"、"Anthropic vs Amazon 自家"两个维度,结论更有说服力
- 三个的输入/输出 token 单价都不高,3 篇样本文本测下来总成本可以忽略不计（预计几美分以内）

## 二、对比维度定义

| 维度                 | 怎么量化                                                                                                             |
| -------------------- | -------------------------------------------------------------------------------------------------------------------- |
| 听话程度（格式合规） | 模型返回的 JSON 能否直接通过`trip_schema.json` 校验（复用 `app/extraction.py` 里 `parse_and_validate` 的校验逻辑）,3 篇样本里通过几篇 |
| 抽取准不准           | 人工核对：文本里提到的地点（places）、日期有没有被漏掉或编造,记录 漏抽数 / 编造数                                    |
| 速度                 | 代码里对每次调用计时（调用开始到收到响应的秒数）,取 3 篇的平均值                                                     |
| 费用                 | 记录每次调用的 input/output token 数,按 Bedrock 官网单价换算成美元                                                   |

## 三、实测对比表（2026-08-03 跑完，`ML/results/*.json` 为原始输出）

> 候选模型换成了实际能申请到的版本：Claude Haiku 4.5 / Claude Sonnet 4.5（原计划测 3.5，
> 申请时 Bedrock 上是这两个新版本），Amazon Nova Lite 不变。漏抽/编造是逐条对照
> `samples/ground_truth/sample_1~3.json` 人工核对的，schema 校验通过不代表内容对——三个模型
> 输出的 JSON 全部合法，但地点数量和内容差别很大。

| 模型 | 3 篇 schema 校验通过率 | 漏抽 / 编造情况（对照 ground truth 人工核对） | 平均耗时 | 预估总费用 |
|---|---|---|---|---|
| Claude Haiku 4.5 | 3/3 | 漏抽 0 处；**编造 8 处地点**（把没写具体名字的住处当成地点，如 sample_1 的 "Bugis"、sample_2 的 "Clarke Quay"；把只是路过/参照的地标当成独立地点，如 sample_1 的 "Sentosa Island"、sample_3 的 "Sultan Mosque"/"Little India"/"Chinatown"；还有把一个地点拆成两条，如 "Chinatown Street Market" 又单独拆出 "Pagoda Street"）；3 篇里有 1 篇（sample_1）给 dates 编了年份 | 4.26s | $0.00889 |
| Claude Sonnet 4.5 | 3/3 | **漏抽 2 处**（sample_1 的 Universal Studios Singapore / Wings of Time 没有作为独立地点输出，被塞进了编造出来的 "Sentosa Island" 的 activities 里）；编造 3 处地点（sample_1 的 "Bugis"、"Sentosa Island"，sample_2 的 "Clarke Quay"）；3 篇里有 1 篇（sample_1）给 dates 编了年份 | 5.13s | $0.02474 |
| Amazon Nova Lite | 3/3 | **漏抽 0 处，编造 0 处地点**——3 篇的地点数量和内容跟人工标注的 ground truth 完全对齐，没有多算也没有少算；3 篇里有 2 篇（sample_1、sample_2）给 dates 编了年份 | 1.62s | $0.00034 |

## 四、结论（跑完测试后填）

- **最终选择：Amazon Nova Lite**（抽取阶段）
- **理由**：地点级别的漏抽/编造都是 0，三个模型里唯一跟人工标注的标准答案完全对齐的；同时速度最快（比 Haiku 快 ~2.6 倍、比 Sonnet 快 ~3 倍）、成本最低（比 Haiku 便宜 ~26 倍、比 Sonnet 便宜 ~73 倍）。贵/慢不代表更准，这次测试里价格最高的 Sonnet 反而漏抽了 2 个真实地点。
- **权衡说明**：
  - Nova Lite 在 3 篇里有 2 篇仍然给 `dates` 编造了年份，说明"不许编年份"这条规则光靠 system prompt 约束不够稳，三个模型全部中招（Haiku 1/3、Sonnet 1/3、Nova 2/3），**这是 prompt/校验层面要修的通病，不是换模型能绕开的**——建议后续在 `extraction.py` 的 `parse_and_validate` 里加一道"年份合理性"校验，或者干脆过滤掉模型编的年份、只留月日。
  - 放弃 Sonnet 的代价：Anthropic 家族"理解力更强"的直觉在这次测试里没体现出来——它反而更容易把辅助信息（Sentosa Island 这种参照地标）"脑补"成一个真正去过的地点，然后把两个真实地点的内容塞进去，造成漏抽。样本量小（3 篇），这个结论不一定能推广，但至少说明"贵的模型更靠谱"不能默认成立，值得以后多测几篇再复核。
